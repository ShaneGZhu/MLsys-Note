# 一、Agentic Inference Challenge

## KV Caching Thrash

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=f66d6d3885d04f86bacde0600aa5ac32&docGuid=1FisqIk_wPEAwm)

Agent workflows由****reasoning阶段****（消耗GPU资源）和****Acting阶段****（即不消耗GPU的工具调用）组成。在Acting阶段，request-aware serving engine（例如vLLM、SGLang）将Acting workflow的KV cache视为可驱逐的空闲内存。

然而，在高并发服务场景下，几乎所有的GPU内存都被工作流KVcache占用（Step 1）。

Reason workflow然后抢占最初属于Acting工作流的KVcache（Step2）。当这些被抢占的workflow稍后重新进入reasoning阶段时，它们又会驱逐其他workflow的KVcache（Step3和4）。

这种连锁反应的驱逐迫使大量workflows从头开始重新计算整个轨迹的Prefill，大大增加了每个请求的端到端延迟。

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=3bfb40231f3042c889dfac9a035c46c2&docGuid=1FisqIk_wPEAwm)

我们评估了在单个H100节点上使用GLM4.6为miniSWE代理提供服务：随着并行LLM代理工作流数量的增加，KV缓存命中率显著下降，每个请求的平均端到端延迟急剧上升。

## Memory imbalance

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=bf5e3ffaf2a54ddfb1e0574b40ce317e&docGuid=1FisqIk_wPEAwm)

与请求级服务request-level serving不同，多节点Agent服务不能简单地专注于负载平衡。由于同一工作流中的请求共享大量的KV缓存前缀，因此将它们路由到同一GPU节点会产生较高的KV缓存命中率。

然而，如上图所示，当内存压力不均匀时，KV-aware routing 会加剧节点之间的内存不平衡。尽管SGLang Gateway引入了一种在内存不平衡情况下切换到负载平衡路由器的算法，但它缺乏多节点和复杂代理工作负载所需的适应性，通常需要手动调整系数。

****简而言之，现有的Router无法动态平衡KV缓存位置和负载平衡之间的权衡，导致多GPU节点服务中的吞吐量次优。****

## unrecycled resource

Agentic workflows 会引入工具所需要的环境（Docker容器、沙盒、API会话），这些环境在工作流完成后很长一段时间都会持续存在。如果没有生命周期感知的回收，这些僵尸资源会消耗磁盘和内存，导致4倍的不必要的存储开销。如果工具资源没有及时回收，磁盘压力就会不断累积，直到节点遇到存储瓶颈。

# 二、Program Abstract

ThunderAgent 将每个 agentic workflow 封装成一个有状态的 ****Program****：这是驱动整个系统中调度、路由和资源管理的核心控制单元。

## what is Program

提供了六个字段将stateless的请求转化为可调度的程序：

1. ﻿$ID$ - 程序标识符 (Program Identity)
    

- 基础含义：程序的全局唯一标识符（Unique global identifier）。
    
- 核心作用：将来自同一智能体任务的所有多轮请求链接为一个完整的单元。它是让“程序级调度（program-level scheduling）”成为可能的核心纽带。
    

1. ﻿$c$ - 上下文长度 (Context Length)
    

- 基础含义：上下文中包含的 Token 数量。
    
- 核心作用：实时跟踪每个程序的 KV Cache 内存占用量。当系统面临内存压力时，调度器可以依据此指标驱逐（Evict）恢复成本最低的程序。
    

1. ﻿$\mathcal{T}$ - 工具环境 (Tool Environments)
    

- 基础含义：该程序所需的工具环境集合。
    
- 核心作用：指代与该程序绑定的所有工具资源（如容器 Containers、沙箱 Sandboxes）。当程序终止时，系统会自动回收这些环境资源。
    

1. ﻿$\mathcal{L}$ - 后端位置 (Backend Location)
    

- 基础含义：为保证空间局部性（spatial locality）而分配的后端 GPU 节点位置。
    
- 核心作用：记录当前是哪个 GPU 节点托管了该程序的 KV Cache。系统会将该程序的后续请求精准路由到同一个节点，以维持上下文的局部性，避免不必要的数据传输。
    

1. ﻿$\tau$ - 执行阶段 (Execution Phase)
    

- 基础含义：标识程序的当前执行阶段：推理（Reasoning, R） 或 行动（Acting, A）。
    
- 核心作用：推理阶段是 GPU 密集型的；而行动阶段是工具交互密集型，此时 GPU 处于空闲状态。该字段使调度器明确知道何时可以从处于空闲（Acting）阶段的程序中临时回收 GPU 资源。
    

1. ﻿$s$ - 调度状态 (Scheduling State)
    

- 基础含义：程序的全局生命周期调度状态，包含三个枚举值：活跃（Active）、暂停（Paused） 或 终止（Terminated）。
    
- 核心作用：允许系统跨不同节点暂停和恢复程序，从而在集群中实现高效的负载均衡（load balancing）。

# 三、Program-Aware Scheduler and Resource Management

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=6d23a90ebe394c84b3c472c43314f1a5&docGuid=1FisqIk_wPEAwm)

ThunderAgent的多节点调度算法以程序粒度运行：

- 监控器定期检查每个GPU节点，并pause累积了很多Acting program防止kvcache thrashing；
    
- 暂停的程序被放置在Global Waiting Queue中；
    
- 当监控器检测到某个节点未得到充分利用时，排队的程序会以负载均衡的方式被分配到不同的节点上，实现整个集群的负载均衡；
    
- 当Program完成时，调度器更新相关工具资源的引用计数器，如果计数器降至0，则动态释放未使用的资源；
    

## Periodic Monitor

在agentic工作负载中，即使没有新的请求或程序到达，KV缓存也会发生抖动，因为在解码过程中上下文长度会持续增长，默默地超过GPU节点之外的内存。为了捕捉到这种情况，ThunderAgent采用了一个定期监视器，****以固定的时间间隔Δt评估每个GPU节点的内存使用情况****，****从而在内存压力达到高阈值之前对其进行提前检测。****

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=c178d708a8304cd38533efc99c2d5aae&docGuid=1FisqIk_wPEAwm)

监控器检查每个节点，并定义为两种状态：thrashing（内存过载）和underutilized（内存利用率低）；

分别对应执行两种决策：

- Pause：在高负载节点上，驱逐program并将其state 存到global waiting queue；
    
- Restore：从排队队列中恢复program到利用率低的节点上。
    

## Global Waiting Queue

引入了一个Score function，通过指定program的执行阶段和上下文长度来打分；

全局等待队列 通过Score function来决定某个Program是执行****Pause****还是****Restore。****

#### 为什么要进行Restore？

现有的KV-aware router将来自同一工作流的所有请求固定到同一GPU节点，以实现缓存局部性。这会导致严重的内存不平衡，一些节点过载，而另一些节点处于空闲状态。

合理的insight：一旦程序暂停，其KV缓存就已经被驱逐。在此基础上，重新计算成本与节点无关——将其发送回原始节点没有KV局部性了。这允许全局队列以负载平衡的方式将可恢复的Program分发到任何具有可用容量的节点上，实现跨节点内存平衡，而不会牺牲活跃程序的KVcache局部性。

## Tool Resource Management

- ****基于Hook的垃圾回收机制：****ThunderAgent实现了生命周期hook，将工具资源持久性和程序的调度状态严格结合起来。当程序终止时，收集器会立即触发回收沙盒、Docker容器、网络套接字和计算Slots。这种生命周期感知策略随着时间的推移保持了近乎恒定的磁盘内存消耗，防止了在没有程序级垃圾收集的系统中观察到的无限资源积累。
    
- ****异步环境准备：****工具执行环境（例如Docker容器、依赖安装）的初始化成本很高。ThunderAgent监控全局等待队列；当高优先级程序接近恢复阈值时，系统在分配GPU内存之前****异步预构建其执行环境****。这种技术有效地隐藏了初始化开销，显著降低了编码代理和科学代理等工具调用繁重工作负载的端到端延迟。
    

# 四、Cost Model 成本建模

采用Space-Time Product 作为主要衡量标准

- Space ($M_x(t)$)：占用的显存大小（在这里主要直接量化为 KV Cache 的 Token 数量）。
    
- Time ($t_x$)：占用的时间。
    

公式如下：$\text{Cost}_x = \int_0^{t_x} M_x(t) \, dt$﻿

论文将多轮 Agent 推理的总成本拆解解成了五个部分，分为 ****“有效”**** （对系统吞吐量有真实贡献）和 ****“无用（损耗）”****：

﻿$\text{Cost}_{\text{total}} \approx \text{Cost}_{\text{decode}} + \text{Cost}_{\text{prefill}} + \text{Cost}_{\text{recompute}} + \text{Cost}_{\text{unused}} + \text{Cost}_{\text{caching}}$﻿

****Cost_decode**** 和 ****Cost_prefill**** 代表对推理吞吐量有实际贡献的有效工作，其余各项均为被浪费的系统开销：****Cost_recompute**** 源于 KV 缓存抖动（thrashing）； ****Cost_unused**** 反映了DP推理后端副本之间的内存不均衡；而 ****Cost_caching**** 则在执行外部工具调用期间持续占用内存而累积。

基于上述成本模型，优化策略是想要最小化 无用的、非生产的开销部分：recompute、unused、caching，以最大化throughput。

# 五、调度策略

## 通过Program-Aware Waiting Queue减少重计算和Caching的开销

****需要清晰的控制active program的数量来减少重计算问题****，论文引入了program-aware wating queue，利用这个队列来调度program，根据上下文长度和Phase，决定某个program执行 或者 被换出。这里引出了两个原子操作：

- ****Resotre****：$P\ \langle ID, c, \mathcal{T}, \emptyset, \tau, \text{Paused} \rangle \leftarrow \langle ID, c, \mathcal{T}, \mathcal{L}', \tau, \text{Active} \rangle$﻿
    
    - 原状态条件：$P = \langle ID, c, \mathcal{T}, \mathcal{L}, \tau, s \rangle$，在执行 Restore 操作前，该程序处于暂停状态（$s = \text{Paused}$），并且尚未分配后端资源（$\mathcal{L} = \emptyset$)
        
    - 新状态更新：通过 Restore(P) 操作，程序被分配到了具有可用容量的新后端节点 $\mathcal{L}'$，同时其调度状态从 Paused 转变为了 $\text{Active}$。
        
- ****Pause****:$P \leftarrow \langle ID, c, \mathcal{T}, \emptyset, \tau, \text{Paused} \rangle$﻿
    
    - 操作行为：Pause(P) 操作会将程序 $P$ 与其当前的后端节点解绑，并释放其 KV Cache 以供抢占。
        
    - 新状态更新：经过该操作后，程序的后端节点位置被清空（$\mathcal{L}$ 变为 $\emptyset$），同时其调度状态更新为已暂停（$\text{Paused}$﻿
        

## 阶段性KVcache检测

我们将DP后端 $\mathcal{L}$ 的抖动条件定义为程序内存需求超过总容量的状态：$C_{\text{total}} < \sum_{p \in \mathcal{L}} c_p$其中 $C_{\text{total}}$ 表示后端 $\mathcal{L}$ 的 KV 缓存池的固定 token 容量。

在解码期间，上下文长度 $c_p$ 增长迅速，即使没有新任务到达，这也可能在执行中途引发内存抖动。实现了一个定期监视器，它以固定的时间间隔 $\Delta t$ 评估内存使用情况，从而允许预先检测和缓解由上下文增长引起的内存压力。

### 水位线机制

通过周期性检查，固定时间间隔评估memory用量，当KV Cache即将发生波动时 触发Pause暂停active program并释放显存；相反，有足够空间就可以从 waiting queue，Restore被暂停的pragrams：

- ****缓解内存压力 (Pause 操作)：****当 KV 缓存即将发生抖动时，系统会调用 Pause 操作来挂起活跃的程序。系统会释放特定大小的内存（$\Delta C = \sum_{p \in \mathcal{L}} c_p - \lambda_{\max} \cdot C_{\text{total}}$），直到总内存使用量降至高水位线（$\lambda_{\max} \cdot C_{\text{total}}$）以下。
    
- ****利用空闲资源 (Restore 操作)：****当后端节点有可用空间时（即内存使用量低于低水位线 $\sum_{p \in \mathcal{L}} c_p < \lambda_{\min} \cdot C_{\text{total}}$），系统会通过 Restore 操作从等待队列中恢复被暂停的程序。在此过程中，系统会确保恢复后的总内存依然保持在高水位线（$\lambda_{\max} \cdot C_{\text{total}}$）之下。
    
- ****水位线机制：****$\lambda_{\max}$ 和 $\lambda_{\min}$ 分别代表内存使用的高水位线和低水位线，两者共同构成了一个滞后窗口（hysteresis window），用于确保调度过程的稳定性。
    
- ****实际应用设置：****在实际部署中，$\lambda_{\max}$ 和 $\lambda_{\min}$ 这两个参数的值都被设置为 1，这是因为跨程序共享的提示词（shared prompt）已经隐式地预留了充足的内存缓冲区。
    

### 时间衰减机制

当Program执行耗时较长的工具调用时，处于Acting阶段的P所占据的 GPU 显存实际上是闲置的。为了在缓存成本（caching cost）和重新计算成本（recomputation cost）之间取得平衡，在抖动检查中引入了时间衰减机制，逐步对处于Acting阶段Pprogram的 token 的有效权重进行衰减。这使得调度器能够主动驱逐长时间闲置的缓存，而不是无限期地占用它们： $C_{\text{total}} < \sum_{p \in \mathcal{L}, \tau=\mathbf{R}} c_p + \sum_{q \in \mathcal{L}, \tau=\mathbf{A}} c_q \times f(t_q) \quad$﻿

其中，$t_q$ 是程序 $q$ 在当前步骤中的工具执行时间。$f(t)$ 是一个旨在平衡 $\text{Cost}_{\text{caching}}$ 和 $\text{Cost}_{\text{recompute}}$ 的时间衰减函数。通过随着时间推移动态降低行动中程序的有效内存优先级，$f(t)$ 鼓励调度器驱逐那些持续处于闲置状态的缓存。

时间衰减函数 $f$ 必须采用以下两种形式之一：

- 连续时间下的指数衰减 (Exponential in continuous time)：$f(t) = e^{-\lambda t}, \quad \text{其中 } \lambda > 0$﻿
    
- 离散时间下的几何衰减 (Geometric in discrete tick time)：$f(k) = x^{-k}, \quad \text{其中 } x > 1$﻿
    

## 按照Shortes-First 策略，决定暂停active programs的子集

基于上述的驱逐和恢复条件，处理抖动（thrashing）剩下的问题是确定暂停哪些活跃程序的子集，从而使重计算成本最小化。

给定一个上下文长度为 $c_i$ 的程序 $P_i$，重新填充其 KV 缓存所产生的重计算成本与 $c_i$ 呈二次方缩放关系，即：

****引理**** $Cost_{recompute} = \int_{0}^{t_{recompute}} c_i(t) dt \propto c_i^2 \quad$﻿

****定义**** （驱逐优化问题）：$\min_{S} \sum_{i \in S} c_i^2 \quad \text{s.t.} \quad \sum_{i \in S} c_i \ge \Delta C \quad $﻿

给定所需的内存释放量 $\Delta C$，调度器的目标是选择一个程序子集 $S$ 进行驱逐，使得释放的容量满足约束，同时最小化总重计算成本。通过选择较小的 $c_i$，该目标函数被严格最小化。

因此，THUNDERAGENT 采取的是贪心策略，****Greedy**** 暂停和驱逐具有最短上下文长度的程序。基于这些分析，在我们的调度器中，我们采用以下分数来恢复和暂停程序：

﻿$S_{restore}(P) = \frac{1}{c_P} + \mathbb{I}(\tau = \mathbf{R}) \quad $﻿

﻿$S_{pause}(P) = \frac{1}{c_P} + \mathbb{I}(\tau = \mathbf{A}) \quad $﻿

其中指示函数 $\mathbb{I}(\cdot)$ 强制程序执行状态（$\tau$）的优先级严格高于上下文长度。两种机制都遵循“最短优先（shortest-first）”策略，以最小化重计算成本。然而，状态指示器 $\mathbb{I}$ 确保调度器优先暂停“行动（Acting）”状态的程序，从而通过回收缓存内存来最小化 $\text{Cost}_{\text{caching}}$，同时优先恢复“推理（Reasoning）”状态的程序，以最大化 $\text{Cost}_{\text{decode}} + \text{Cost}_{\text{prefill}}$。

****公式含义：****这两个公式定义了调度器对程序进行恢复和暂停操作时的优先级打分机制。

- 基础分数为 $\frac{1}{c_P}$：上下文长度 $c_P$ 越短，分数越高，落实了“最短优先”的贪心策略。
    
- 指示函数 $\mathbb{I}(\cdot)$：作为一个绝对的权重加成项（满足条件为1，否则为0），它保证了程序状态的最高优先级。
    

## ****global program-aware waiting queue****

论文提到一个关键点：****任务一旦被休眠，它的 KV Cache 就被清空了（Evicted）****。既然缓存都没了，它重新启动时去哪台机器都一样。所以，干脆把所有排队的任务拉到一个“全局总队列”里。哪台机器有空，就从总队列里抓一个任务进去算。

该设计的核心动机在于，$\text{Cost}_{\text{unused}}$ 仅在被暂停的程序滞留在等待队列中、而同时某些副本仍有空闲内存时才会产生。此外，一旦程序被暂停，其 KV 缓存就被假定为已被驱逐，这使得它的重计算成本变为与节点无关的（node-agnostic）。这允许我们在不牺牲 KV 缓存局部性的情况下改善跨节点的内存均衡。恢复（restore）策略与负载均衡对齐，而不是严格的 KV 感知路由，从而使得被暂停的程序能够被分发到任何具有可用内存容量的副本上。因此，全局队列限制了未使用成本，使得在 $\Delta t$ 周期内每个节点的 $C_{\text{unused}} < c_{\text{min}} \cdot \Delta t$，其中 $c_{\text{min}}$ 代表暂停程序中的最小 token 长度。

> 如果一个节点在 $\Delta t$ 期间的闲置显存 $\ge c_{\text{min}}$，那么调度器必然会立刻把队列里那个最小的程序拿出来放进这个节点运行。此时，这部分显存就不再是“闲置”状态了。
> 
> 因此，任何节点在任何时刻，其无法利用的闲置显存必定严格小于当前等待队列中最小程序的显存需求（$c_{\text{min}}$）。
> 
> 这意味着调度器：****只要节点上还有空闲的显存，调度器就会去全局队列里找程序来填满它****。

# How To Use

# Step 1 — Install vLLM & ThunderAgent

pip install vllm

git clone https://github.com/HaoKang-Timmy/ThunderAgent.git

cd ThunderAgent

pip install -e .

# Step 2 — Start vLLM

# Start vLLM server on port 8000

vllm serve Qwen/Qwen3-32B --port 8000

# Step 3 — Start ThunderAgent

# Start ThunderAgent on port 9000, and connect it to vLLM at port 8000

thunderagent --backend-type vllm --backends http://localhost:8000 --port 9000

# connect client to ThunderAgent router (port 9000)

# ThunderAgent would forward the requests to vLLM backend (port 8000)

from openai import OpenAI

client = OpenAI(base_url="http://localhost:9000/v1", api_key="dummy")

response = client.chat.completions.create(

    model="Qwen/Qwen3-32B",

    messages=[{"role": "user", "content": "Hello!"}],

    extra_body={"program_id": "my_agent_001"}

)

print(response.choices[0].message.content)
